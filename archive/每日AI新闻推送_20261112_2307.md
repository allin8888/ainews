### 1. Google 发布 Gemini Decisions API 与 Gemini Decision 1：单次前向传播完成最多 1,000 项封闭式多模态决策（Google）

**第一信源**：[Google 官方发布](https://blog.google/innovation-and-ai/technology/developers-tools/gemini-decisions-api/)；[Decisions API 文档](https://aistudio.google.com/docs/decisions-api)；[Gemini API 更新日志](https://ai.google.dev/gemini-api/docs/changelog#11-11-2026)；[OpenRouter 模型页](https://openrouter.ai/google/gemini-decision-1)。

**首发时间**：2026-11-11 18:00 UTC / 2026-11-12 02:00 北京时间，取官方文章结构化字段 `datePublished` 与官方博客 RSS 条目；页面可见文本仅显示 `Nov 11, 2026`，不据此虚构时分。同批官方 X 帖集中在 18:15–18:26 UTC，作为交叉印证，不替代文章首发时刻。

**发生了什么**：Google 在 Gemini API 中新增 `decisions` 端点，底层模型为 `gemini-decision-1`。它面向工具选择、策略检查、模型路由、内容分级等「有界选择」，不是新的通用生成模型；一次请求可携带一份多模态输入与最多 1,000 个彼此独立的问题，返回概率与置信度。官方同时列出 OpenRouter、LangChain、Vercel、LiteLLM、Pydantic AI、Pipecat、LiveKit、OpenCode 的集成正在 rollout，`google-genai` SDK 已可用。

**技术机制**：核心是取消逐 token 解码，在单次前向传播中对候选选项打分。三类问题原语：`noul`（是/否条件成立的概率，可附真假判据）、`choice`（2–255 个候选，返回赢家与每个候选的归一化概率）、`score`（从 0 起的有序 rubric，返回连续加权分与各级概率）；三类可在同一请求内混用，共享同一份 `input`。`input` 沿用 Interactions API 的 `Content` 块格式，支持文本、图像、音频、视频、PDF，图像与视频可调分辨率以控制视觉细节与 token 成本。每个答案带 0–1 置信度，供代码把模糊样本转交回退或人工复核。共享输入每请求只计费一次，每题只增加自身的 instruction 与 criteria token。

**关键指标/资源**：官方称端到端 150–250 ms、模型计算中位 50–100 ms，在最多 16K tokens 上下文下从 1 题到 100 题延迟近乎持平；API 输入上限 256K tokens；输入 $0.10/1M tokens，输出 token $0，且无 thinking-token、音频转写与 OCR 单独计费；在共享基准套件上比 Gemini 3.5 Flash-Lite + Interactions API 便宜近 5 倍；Gemini Notebook 用于实时意图分类时日常查询延迟最多降低 40%。以上均为 Google 官方自述数据，未见第三方复现；官方称「全集领先、校准误差最低」，但正文未给出各基准名称、分数或 ECE 数值。

### 2. PyTorch 与 IBM 用 AI 编程智能体不到一周把 SGLang 接入 Spyre：约 1,500 行插件、约 3.6× 吞吐（PyTorch / IBM / RadixArk）

**第一信源**：[PyTorch 官方博客](https://pytorch.org/blog/integrating-sglang-into-spyre-in-under-a-week-with-ai/)；[torch-spyre 仓库](https://github.com/torch-spyre/torch-spyre)；[vLLM Spyre 后端参考实现](https://github.com/torch-spyre/spyre-inference)。

**首发时间**：2026-11-12 06:45:25 −08:00，即 14:45:25 UTC / 22:45 北京时间，取官方页面 `datePublished`；官方博客 RSS 抓取时间与之吻合。页面另有 03:16:04 −08:00 字段，本期不把它当作首发时刻。

**发生了什么**：IBM 两人团队借助 AI coding agents，在不到一周内把 SGLang 服务栈（含内置前缀共享）接入 IBM Spyre 加速器，产出一个约 1,500 行的开源插件与 4 个小补丁。文章把这件事定位为「集成」而非新硬件、新模型或新框架发布，并披露了智能体所依赖的参考代码来源与 SGLang 扩展点结构。

**技术机制**：可行性来自两层既有抽象——`torch-spyre` 把 Spyre 注册为 PyTorch 设备并接到 `torch.compile`，用标准 PyTorch API 暴露算子；SGLang 则提供 platform registration、attention backend、KV pool、operator dispatch 四类边界清晰的扩展点。AI coding agents 以既有 vLLM Spyre 后端（约 3,500 行）及其中 PyTorch 版算子实现为参考代码，把适配工作收敛到接口对齐：复用 attention 基类，只覆写内层 scaled dot-product attention；RMSNorm、SiLU、GeLU、rotary embedding、linear 接到 SGLang 算子分发；KV pool 因设备无关，只需覆写一个 buffer 创建方法，原先依赖 Triton 的分配改由 PyTorch 处理。4 个补丁中 2 个让既有执行路径摆脱 CUDA 专属依赖（可惠及其他加速器），2 个把 Spyre 注册为受支持设备与「不使用 Triton」的 attention backend。RadixCache 的前缀共享在 SGLang 调度层完成，抵达加速器之前即已解析，因此无需任何 Spyre 专用改动。官方示例为 `sgl.Engine(model_path=..., device="spyre", attention_backend="spyre_paged", dtype="float16", page_size=64, max_running_requests=1, disable_cuda_graph=True)`。

**关键指标/资源**：两人、不到一周、约 1,500 行插件、4 个补丁；SGLang on Spyre 约为 `torch-spyre` 参考 PyTorch 推理实现的 3.6× 吞吐；在 Granite 3.3 8B 与 Gemma 4 26B A4B 的已测负载上与 vLLM 持平（官方图以 vLLM = 1.0 归一化）；对照的 vLLM Spyre 后端约 3,500 行，其中约三分之二的行数差来自复用 attention 基类。以上为作者团队自述实测，未见第三方复现；官方未披露绝对吞吐、批大小、序列长度、功耗与测试环境完整配置。

### 4. vLLM-Omni 在 Vera Rubin 上实现 MiniMax H3-Image Day-0 支持：4K 生成中位 0.87 秒（vLLM / MiniMax）

**第一信源**：[vLLM 官方博客](https://vllm.ai/blog/2026-11-12-minimax-h3-image-rubin)；[H3-Image 开源权重](https://huggingface.co/MiniMaxAI/MiniMax-H3-Image)；[基准数据 CSV](https://vllm.ai/assets/figures/minimax-h3-image-rubin/api-workload-results.csv)；[VAE 对照测量](https://vllm.ai/assets/figures/minimax-h3-image-rubin/vae-decoding-control.json)；[AMD / XPU / NPU / MUSA recipes](https://github.com/vllm-project/vllm-omni/tree/main/recipes/MiniMaxAI)。

**首发时间**：官方文章标注 `November 12, 2026`（`datePublished` 为日粒度）；官方博客 RSS 聚合时间 `2026-11-12T00:00:00Z`，落在窗口内。本期按官方日期入窗，不把日粒度时间反推为具体发布时分，也不使用转载时刻替代。

**发生了什么**：vLLM-Omni 在 NVIDIA Vera Rubin 上完成开源权重模型 MiniMax H3-Image 的 Day-0 推理支持。H3-Image 用一个 checkpoint 同时承担文生图与图像编辑，六步采样原生输出高分辨率图像（无需超分），最多支持 16 张参考图。此次工作同时给出 10 种 NVIDIA 硬件的实测，以及 AMD、Intel、华为昇腾、摩尔线程的可运行 recipe，属于推理引擎对新硬件与新模型的适配发布，不是新模型发布。

**技术机制**：模型由 Qwen3-VL 编码器、33.1B dense DiT 与图像 VAE 组成；一张原生 4096×4096 图对应 16,384 个目标图像 token，需跨六步去噪，再经 VAE 解码，因此优化聚焦三处。① DiT：Blackwell/Rubin 上对 eligible 线性层启用 MXFP8 GEMM（Rubin 用 FlashInfer CuTe-DSL kernel，attention 用 `TRTLLM_ATTN`），Ulysses SP4 把序列切到四卡、DiT TP1 保持权重复制，AdaLN caching 复用输入输出与权重完全一致的 conditioning 投影；编码器与 VAE 保持原精度，Hopper/Ampere 走 BF16。② 解码：VAE 独立图块跨 GPU 分发，再用 CUDA Graph replay 叠加多 CUDA stream，让各图块重叠执行。③ 显存：单卡部署用 layerwise CPU offload（RTX 5090/5080 卸载 DiT 与文本编码器、VAE eager 解码；RTX 6000D / PRO 6000 让 DiT 常驻并用 VAE CUDA Graph）。Rubin bringup 还修了一处反复 4K 请求触发的输出传输 stall：把最终图像布局转换移到 CPU、在传完 uint8 张量之后执行，并用回归检查确认像素不变。次级收益来自 SP4 / SP2×DP2 / SP1×DP4 三种并行配置的分别调优，而非单一「最优配置」。

**关键指标/资源**：SP4、并发 1 时中位 0.866 s（p95 0.944 s），为 GB200 的 2.21×、GB300 的 1.64×；SP1×DP4 四副本在并发 8 达 6,115 images/hour（中位 4.411 s），SP4 在并发 2 达 4,407 images/hour（中位 1.421 s），副本带来 38.7% 吞吐增益；同一 SP4 配置下 Rubin 峰值吞吐为 GB200 的 2.20×、GB300 的 1.60×。4×GB300 上 4K 文生图 1.48 s、单参考图编辑 1.77 s；单 H200 2K BF16 1.49 s；单 RTX 5090（CPU offload）分别为 52.29 s / 61.45 s。VAE BF16 对照：解码 2.635 s → 0.213 s，端到端约 4.0 s → 1.6 s（2.5×）。6,115 images/hour 外推为 146,755 张/天；按 MiniMax 官方 Standard 4K 定价示例 $0.06879/张作为假设售价，推算 $105.16/GPU/hour（100% 计费利用率）或 $78.87（75%）。以上均为作者实测或外推，未见第三方复现；日产能是速率外推而非 24 小时压测，收入为税前毛收入、未扣运营成本。

**为什么重要**：这条工作把「4K 扩散模型能否进入交互式服务」拆成了可核查的工程分解——序列并行、低精度 GEMM、条件投影缓存、VAE 图块并行与图重放各自贡献多少，以及延迟最优（SP4）与吞吐最优（SP1×DP4）是两个不同工作点。官方主动声明两类数字来自不同 prompt 语料、HTTP client 与统计量（短 prompt serving benchmark vs. 1,292 字符 coffee-product prompt 三 seed 均值），并给出 CSV 与 JSON 原始数据，这种口径披露方式本身值得推理服务报告借鉴。跨 NVIDIA / AMD / Intel / 昇腾 / 摩尔线程的 recipe 也降低了非 CUDA 环境复现门槛。

**限制**：官方明确这些数字比较的是「已部署系统」而非隔离 GPU 架构——GPU 数、精度、显存放位、allocator 设置均随配置变化；1K 检查实际在 2048×2048 生成后缩放，不代表原生 1K 扩散计算量。0.87 s 与 6,115 images/hour 分别来自 SP4 与 SP1×DP4，不能同时成立。收入与日产能均为外推，且实际托管 API 计费随文本 token 用量变化。AMD / Intel / 昇腾 / 摩尔线程部分为社区各自工作负载下的验证，不与 NVIDIA 匹配性能数字直接可比。本期未复跑任何基准。

**开放与许可**：vLLM-Omni 及 recipes 为公开仓库；H3-Image 为开源权重模型，权重托管于 Hugging Face。具体许可证须按权重卡与代码仓库分别核对，本期不将「开源权重」等同于统一开源许可或可商用授权。

## 趋势简评

- **Agent 的成本结构正在被重新切分**：Gemini Decisions API 把高频判断变成便宜的打分调用，LiveKit 把低频控制台操作交给人授权的智能体，PyTorch/IBM 案例则显示后端集成的人力成本在压缩。三者共同指向「按动作风险与频率分配模型、权限与人类审批」，而不是让一个通用模型包办所有环节。
- **权限边界比能力清单更值得读**：LiveKit 的短时令牌、admin 限定与计费动作确认，与 PyTorch 案例里「参考实现 + 稳定扩展点」的约束，都是把智能体能力关进可审计边界的做法。能力变强时，边界设计是否同步，是后续观察重点。
- **推理数字必须带工作点**：vLLM 的 0.87 s 与 6,115 张/小时不能同时引用，Gemini 的 150–250 ms 也只在官方特定上下文范围内近乎持平。把「最优延迟」「最优吞吐」「外推产能」混作一个指标，是当前推理服务报道最常见的失真来源。
